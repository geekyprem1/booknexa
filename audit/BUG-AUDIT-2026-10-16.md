# BookNexa bug audit — 16 October 2026

**16 confirmed source-level defects: 8 high priority (P1), 8 medium priority (P2).**

This is the number found in this audit, not a guarantee that the entire application has exactly 16 bugs. Reviewed admin fulfilment, subscription/credit logic, feature gating, job orchestration, cover generation, exports, auth/status guards, and support. Application code was not changed during this audit.

## Verification and limits

- `npm.cmd run typecheck`: passed.
- `npm.cmd run build`: passed outside the restricted sandbox. The initial sandbox run failed because Turbopack inferred `C:\Users\user` as the workspace root and could not read it; that environment failure is not counted as a product bug. The successful build still warns about multiple lockfiles/root inference.
- Existing offline suites passed: Sudoku 6, Maze 5, Opportunity 6, Coloring 9, Cover V2 32, Cover layout 55 — **113 checks**.
- `node audit/reproduce-bugs.cjs`: **16 independent defect scenarios reproduced**. Results: `audit/reproduction-results.json`.
- The reproductions transpile and execute repository source, substituting controlled database, storage, and AI dependencies. They demonstrate logic under concurrency/failure conditions without live database writes or paid API calls. They are not live browser/payment/provider end-to-end tests, and they do not establish how often each bug has occurred in production.
- The reproduction script asserts the current *broken* outcomes. A successful run confirms defects, not that the application is correct; update these assertions when converting them into regression tests after fixes.

## Findings

### B01 — P1 — Purchased cover access is blocked by the studio redirect

**Evidence:** `app/dashboard/cover/page.tsx:6`, `app/dashboard/cover-v2/page.tsx:63`, `lib/offers.ts:284`, `lib/billing/plans.ts:83`.

Creator Suite, Agency, Reseller, and Unlimited Lite grant `cover: true`. The old `/dashboard/cover` page now always redirects to `/dashboard/cover-v2`, whose gate requires `cover_v2` or the highest plan/Unlimited. A Starter-tier buyer can own one of those offers and still have no usable Cover Studio in the UI. The V1 API still exists, but there is no reachable V1 studio page.

**Reproduced:** All four offers pass `canUseFeature('starter', 'cover', entitlements)` and fail the same check for `cover_v2`; the legacy page redirects to V2.

**Suggested fix:** Preserve a functional V1 studio for `cover` owners, or explicitly reconcile the unified studio's entitlement and cost rules with the sold offers. Do not silently broaden a premium feature without deciding the intended product access.

### B02 — P1 — Unlimited failure refunds mint unspent credits

**Evidence:** `lib/billing/credits.ts:74`, `lib/billing/credits.ts:97`; callers include Cover V2, bundle, publishing-package, and Autopilot failure paths.

`reserve()` returns early for Unlimited, while `refund()` unconditionally adds the requested amount. A failed generation increases an Unlimited user's buffer balance even though no credits were reserved. Bundle over-reservation adjustments can also add credits without a debit.

**Reproduced:** Balance 100, `reserve(4)`, then `refund(4)` yields 104; there was no spend RPC.

**Suggested fix:** Return/store the actual reservation and refund that reservation once. Do not simply consult the user's current Unlimited flag during refund, since an entitlement can change after a real debit.

### B03 — P1 — Changing plans overwrites concurrent credit changes

**Evidence:** `lib/billing/subscription.ts:98`, `lib/billing/subscription.ts:109`.

`changePlan()` reads the balance and later writes an absolute `credits_remaining`. A generation reservation, refund, or grant between those operations is overwritten. This can restore spent credits or lose newly granted/refunded credits, and the ledger no longer matches the balance.

**Reproduced:** Starting at 100, a concurrent 10-credit spend followed by a 120-credit plan grant should leave 210; it leaves 220.

**Suggested fix:** Change plan metadata and apply a ledger-backed balance delta in one database transaction with a subscription-row lock.

### B04 — P1 — Concurrent offer grants lose paid access

**Evidence:** `lib/billing/subscription.ts:69`, `lib/billing/subscription.ts:74`.

`applyOfferMeta()` merges entitlements in JavaScript using a previously read snapshot. Two admins granting different offers concurrently can both succeed while the last write removes the other grant's flags.

**Reproduced:** Concurrent DFY and Creator Suite grants leave the Creator Suite flags but lose `dfy_assets: true`, so the successfully granted DFY library access disappears.

**Suggested fix:** Merge JSONB into the current database value atomically, ideally inside the full offer-delivery transaction.

### B05 — P1 — Failed offer delivery can leave access without credits or history

**Evidence:** `lib/admin/users.ts:268`.

`adminGrantOffer()` first commits plan/entitlement metadata, then grants credits, then records offer history. A credit-RPC failure leaves the unlock in place, but reports failure and never creates the grant history. The new Granted Offers column therefore cannot show this partial delivery. Retrying lacks a durable delivery identifier for safely resuming a particular purchase.

**Reproduced:** An Unlimited grant commits the unlock; the credit operation fails; the operation rejects and no `grant_offer` entry is written.

**Suggested fix:** Persist a durable offer-delivery record and atomically apply metadata, credit ledger, and delivery history. Use a delivery/purchase identifier to distinguish a retry from an intentional additional grant.

### B06 — P1 — Bundle and Autopilot generation bypass fair-use caps

**Evidence:** `lib/billing/caps.ts:69`, `app/api/bundle/route.ts:120`, `app/api/autopilot/route.ts:89`.

Caps classify individual book/image features, but the bundle endpoint checks only `factory` and Autopilot checks only `autopilot`. Neither is a classified book/image action, so cap checking immediately returns. The nested generators never check the individual book caps. A user already at the daily/monthly limit can continue producing books through these routes, including paid image generation through bundles.

**Reproduced:** A simulated 1,000 completed generations blocks `coloring`, but `factory` and `autopilot` perform no count query and pass.

**Suggested fix:** Reserve cap capacity for each planned output, including image capacity where relevant, and settle/release it with generation. An atomic reservation also prevents simultaneous requests from exceeding the limit.

### B07 — P1 — Cancelled/stale Autopilot attempts keep generating and charging

**Evidence:** `lib/books/ebook-pipeline.ts:43`, `lib/books/autopilot-pipeline.ts:108`, `lib/jobs/job-runner.ts:46`.

`progressUpdater()` throws when the job attempt no longer owns its lease, but the ebook pipeline catches every progress error and continues. Autopilot keeps reserving per-book credits and writing books after cancellation/recovery. Its runner also ignores a false `markCompleted()` result, unlike the ordinary book branch. An old attempt and a retry can overlap, write run state, and generate duplicate books.

**Reproduced:** The actual Autopilot and ebook pipeline code receives nine lost-attempt progress errors, yet completes all three mocked books and consumes 30 credits.

**Suggested fix:** Propagate lease-loss/cancellation errors, validate the attempt before each per-book reservation and persistence step, and fence run/angle updates. Persist per-book reservation identities for restart-safe settlement.

### B08 — P2 — Unset Cover V2 concept count silently becomes one

**Evidence:** `lib/cover-v2/config.ts:83`.

The declared default is two, but an unset/blank `COVER_V2_CONCEPTS` becomes `Number('') === 0` and is clamped to one. Operators who configure only the necessary API keys receive fewer concepts than the documented default.

**Reproduced:** With no concept-count environment variable, `coverV2Config().concepts === 1`.

**Suggested fix:** Return `DEFAULT_CONCEPTS` for an empty value before numeric parsing.

### B09 — P2 — Cover verification can approve the wrong title

**Evidence:** `lib/cover-v2/verify.ts:18`, `lib/cover-v2/verify.ts:48`.

Phrase matching accepts raw substrings instead of complete word sequences, so `ART` is accepted inside `SMART`. Normalization also removes non-ASCII scripts; a Hindi-only requested title becomes empty and is treated as an exact match against unrelated readable English text. Both paths can deliver a cover with `textVerified: true` even when the requested title is absent.

**Reproduced:** Requested `ART`, read `SMART`: passes. Requested `नमस्ते दुनिया`, read `UNRELATED ENGLISH TEXT`: passes.

**Suggested fix:** Preserve Unicode letters/numbers, require a nonempty normalized required title, and compare whole token sequences. Apply the same rules to author names.

### B10 — P2 — ZIP exports mislabel Cover Studio PNGs as PDFs

**Evidence:** `app/api/cover/[id]/use/route.ts:77`, `app/api/publish-package/[id]/route.ts:48`, `app/api/bundle/[id]/export/route.ts:41`.

Applying a Cover Studio variation sets a book's `cover_key` to the PNG object. Non-ebook publishing packages and bundle exports always call the asset `cover.pdf`, without converting its bytes. PDF readers and upload validators receive a PNG disguised as a PDF.

**Reproduced:** The publishing ZIP asset has name `cover.pdf` but starts with the PNG signature rather than `%PDF`.

**Suggested fix:** Preserve the real file format/name, or build a proper print-cover PDF using the book's geometry. Check both export paths.

### B11 — P2 — Ebook page count is the number of chapters

**Evidence:** `lib/books/ebook-pipeline.ts:106`, `lib/export/pdf.ts:27`, `app/api/publish-package/route.ts:53`.

Completed ebooks store `built.chapters.length` as `page_count`. The PDF actually has title/contents pages plus flowing chapter content. User book lists display the wrong page total, and publishing price calculations use this incorrect value. Rewriting chapters cannot update an accurate page count because none is computed.

**Reproduced:** A generated ebook containing three very long chapters is saved as three pages.

**Suggested fix:** Measure the rendered print PDF at the selected trim, store its real page count, and invalidate/recompute after chapter edits. If not yet rendered, represent page count as unknown rather than using chapter count.

### B12 — P2 — Support attachments cannot be opened in the app

**Evidence:** `components/support/ticket-thread.tsx:27`, `app/dashboard/support/[id]/page.tsx`, `app/admin/tickets/[id]/page.tsx`.

The upload flow stores private attachments, but both ticket pages render them as plain spans. There is no attachment download API or signed link. The tooltip says to open them from the admin panel, but the admin page uses the same noninteractive component.

**Reproduced:** Server-rendered attachment markup contains its filename but no link or button.

**Suggested fix:** Add an attachment-download route that verifies ticket ownership/admin status and the attachment's permitted storage key, then returns a short-lived signed URL. Do not sign arbitrary client-submitted keys.

### B13 — P2 — First subscription initialization is not concurrency-safe

**Evidence:** `lib/billing/subscription.ts:23`, `supabase/migrations/0013_billing.sql:19`.

Two initial requests can both read no subscription and attempt inserts. The unique `user_id` constraint rejects one, and the helper throws instead of reloading the subscription created by the other request. Parallel dashboard/generation requests on a fresh account can fail intermittently.

**Reproduced:** Two simultaneous `getOrCreateSubscription()` calls yield one success and one duplicate-key error.

**Suggested fix:** Insert with conflict handling and select the resulting row; keep signup-credit ledger creation idempotent and transactional.

### B14 — P2 — Analytics failure refunds a successfully saved Launch Kit

**Evidence:** `app/api/publish-package/route.ts:101`, `app/api/publish-package/route.ts:109`.

The package upsert is committed before the completion usage record. If analytics insertion fails, the shared catch reports generation failure and refunds the credits even though the generated package remains available. Users see a failure for successful work, and the account gets a free completed generation.

**Reproduced:** Package save succeeds, completion usage throws, HTTP 500 is returned, and the full reservation is refunded.

**Suggested fix:** Separate the authoritative save/settlement from best-effort analytics. Do not refund after the completed result is committed.

### B15 — P2 — Admin user creation can report failure after creating the account

**Evidence:** `lib/admin/users.ts:180`, `lib/admin/users.ts:201`.

The auth account is created and email-confirmed before offer provisioning. If subscription/offer provisioning fails, the API reports create-user failure but leaves the account active. Trying again encounters an existing email. Requested privileged-role writes also ignore returned database errors, so provisioning can silently create the wrong role.

**Reproduced:** Successful `createUser()` followed by failing offer metadata leaves the confirmed auth account in place; no compensation or partial-success response occurs.

**Suggested fix:** Verify role writes and explicitly model provisioning states. Safely compensate a newly created account or return the created account with a resumable fulfilment failure, so retry does not recreate it.

### B16 — P1 — Unlimited buyers still pay credits for queued book generation

**Evidence:** `lib/billing/credits.ts:78`, `lib/jobs/job-queue.ts:27`, `supabase/migrations/0019_job_credit_integrity.sql:88`.

The route's `reserve()` preflight skips charges for Unlimited, but `createJob()` still forwards the original `_cost` to `job_create_with_reservation`. That SQL RPC always checks/deducts `v_cost` and never checks the Unlimited entitlement. Normal queued generators therefore consume Unlimited buffer credits and eventually reject generation with insufficient credits. The SQL retry path also relies on the stored nonzero cost.

**Reproduced:** An Unlimited subscription still sends `p_credit_cost=4`. The installed SQL definition debits `v_balance - v_cost` with no entitlement exemption.

**Suggested fix:** Resolve and persist the effective credit cost inside the locked database reservation transaction. Define retry behavior when ownership of Unlimited changes; keep consumed/refunded ledger state consistent.

## Recommended fix order

1. **B16, B02, B03:** make charging/refunding consistent and atomic.
2. **B04, B05, B15:** make offer/user provisioning durable, atomic where possible, and safely retryable.
3. **B01:** restore the access promised by purchased cover offers.
4. **B07, B06:** fence Autopilot attempts and reserve generation-cap capacity.
5. **B10, B11, B09, B08:** correct export formats, print metadata, and cover verification/defaults.
6. **B13, B14, B12:** handle initialization races, analytics errors, and support attachments.

The displayed Free Trial base plan after a successful Reseller/Unlimited add-on grant is **not** counted as a bug: add-ons intentionally retain the base plan. Repeated manual grants adding credits are also not counted by themselves, because the admin action explicitly grants another credit allocation.
